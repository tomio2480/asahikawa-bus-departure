# 🧩 生成物の配置がディレクトリ走査に間に合わなかった

[Issue #132][i132] は「開発サーバーが `sql.js` の wasm を横取りしている」と見立てていた．実際には横取りではない．Vite が起動時に 1 度だけ取る `public/` の一覧に生成物が載らず，静的配信を素通しして `index.html` へ落ちていた．本書に残すのは，症状が特定ファイル名に見えた理由，疑いが外れた過程，切り分けを 1 手で終わらせた観測である．

## 🔍 症状とその見え方

`npm run dev` で起動すると，アプリはデータを読み込めない．`/sql-wasm.wasm` と `/sql-wasm-browser.wasm` だけが `index.html` を返していた．他の `public/` 配下は正常である．

同じ内容を別名でコピーすると，そのコピーは正しく配信される．ここから「この 2 つのファイル名に限って横取りされる」という見立てが立った．`sql.js` は依存の事前バンドル対象であるため，`optimizeDeps` が同名のアセットを奪っている疑いが自然に見えた．

この見立ては誤りである．差は名前ではなく，ファイルが存在し始めた時刻にあった．

---

## ⏱ 実行順序が生んだ穴

Vite の開発サーバーは `public/` を起動時に 1 度だけ走査する．走査の結果は集合として保持され，静的配信の可否判定に使われる．集合に無いパスは配信を素通しし，SPA フォールバックへ回る．

該当箇所は `node_modules/vite/dist/node/chunks/node.js` にある．

```js
// servePublicMiddleware
if (publicFiles && !publicFiles.has(toFilePath(req.url)) || ...) return next();
```

フックと走査の順序は表 1 のとおりである．

表 1. 開発サーバー起動時の実行順序

| 順 | 処理 | 本件との関係 |
|---|---|---|
| 1 | `resolveConfig()`（`configResolved` フック） | ここで置けば走査に載る |
| 2 | `initPublicFiles()` | `public/` を 1 度だけ走査する |
| 3 | `httpServer.listen` | — |
| 4 | `buildStart` フック | 走査より後のため間に合わない |

`vite.config.ts` の `copy-sql-wasm` プラグインは，wasm を `buildStart` でコピーしていた．順序の 4 に当たる．生成物が無い状態から起動すると，集合へ載らないまま配信判定を迎える．

`public/.gitignore` はこの 2 ファイルを無視する．クリーンな作業ツリーからの起動では必ず踏む構造であった．

別名のコピーが配信できた理由も同じ順序で説明が付く．コピーを作った時点でサーバーは起動済みであり，ファイル監視の追加イベントが集合を補っていた．走査に間に合わなくても，走査の後なら拾われる．間に合わない窓は起動処理の内側だけである．

## 🧪 疑いを 1 手で外した観測

`optimizeDeps` の疑いは，サーバーを再起動せずに外せた．稼働中のサーバーはそのままに，2 つのうち片方だけを削除して作り直す．

表 2. 同一サーバー上での応答（`sql-wasm.wasm` のみ削除して再作成した直後）

| パス | ステータス | Content-Type | サイズ |
|---|---|---|---|
| `/sql-wasm.wasm` | 200 | `application/wasm` | 659730 |
| `/sql-wasm-browser.wasm` | 200 | `text/html` | 631 |

依存の事前バンドルの状態は両者で共通である．`node_modules/.vite/deps/sql__js.js` も共通である．差は再作成の有無だけであり，`optimizeDeps` は関与しない．

この 1 手により，Issue が挙げていた切り分け 4 項目のうち 3 つが同時に片付いた．`node_modules/.vite` の削除も，Vite 7 系への降格も，`optimizeDeps.exclude` の追加も不要である．原因が `initPublicFiles` にある以上，どれも的を外す．

変数を 1 つだけ動かせる観測を先に探すと，候補を個別に潰すより速い．

## 🛠 直し方の選択

コピーを `configResolved` へ移した．表 1 の順序 1 に当たり，走査より前に実体が置かれる．

あわせてコピー先を，解決済みの `publicDir` から取るようにした．文字列 `"public/"` の直書きを外すことで，テストから一時ディレクトリを渡せる．

```ts
configResolved({ publicDir }) {
  for (const name of ["sql-wasm.wasm", "sql-wasm-browser.wasm"]) {
    copyFileSync(`node_modules/sql.js/dist/${name}`, resolve(publicDir, name));
  }
}
```

テストは `test/vite-config.test.ts` に置いた．固定したのは 3 点である．`configResolved` を持ち `buildStart` を持たないこと．渡した `publicDir` へ 2 つの wasm を書き出すこと．本番ビルドでも同じ経路を通ること．

1 点目はフック名という実装詳細を固定する．通常は避けるが，本件では不具合の本質そのものが「どのフックか」であるため固定する価値がある．

## 🧭 採らなかった直し方

表 3. 検討したが採らなかった案

| 案 | 棄却理由 |
|---|---|
| `npm run predev` でコピーする | 設定が `package.json` と `vite.config.ts` へ分かれる．`vite build` 側にも同じ配慮が要る |
| `public/` を経由せず `new URL(..., import.meta.url)` で解決する | `sql.js` の `locateFile` は URL 文字列を返す契約であり，配信経路の設計を広く変える．不具合の修正としては過大 |
| 生成物を Git 管理下に置く | 659730 バイトの binary を 2 つ抱える．依存の版と実体がずれる余地も残る |

コピー元の `node_modules/sql.js/dist/...` は相対パスのままにした．`process.cwd()` に依存するが，従来からの挙動であり本件とは無関係である．`config.root` を基準にすると，依存が巻き上げられた構成で逆に壊れる．

## 💡 一般化できる教訓

- 「特定の名前だけ壊れる」に見えたら，名前ではなく時刻を疑う．生成物とそれを読む側で，どちらが先かを確かめる．
- ツールの内部順序は推測せず，`node_modules` の実体を読む．本件は該当箇所が 1 行で，読めば順序が確定した．
- 切り分けの項目を上から順に潰す前に，変数を 1 つだけ動かせる観測を探す．稼働中のサーバーで片方だけ作り直す手が，4 項目のうち 3 つを同時に落とした．
- 自動生成物を無視設定へ入れると，クリーンな状態でだけ踏む不具合が生まれる．手元で再現しない報告は，まず生成物の有無を揃える．
