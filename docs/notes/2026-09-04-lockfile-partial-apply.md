# 🔐 ロックファイルを Windows で部分適用する

`npm audit` の critical・high・low を解消した際（Issue #169，PR #170）の記録．
Windows で `package-lock.json` を再生成せずに複数エントリを動かす手順をまとめる．
あわせて，着手前に置いていた前提が 2 つ外れた経緯と，Bot レビューの読み方を残す．

## 🧭 背景

Issue #169 は `vitest` の critical を扱う．勧告は GHSA-5xrq-8626-4rwp である．
`npm audit` は high と low も 1 件ずつ報告していたが，内容は未確認のままだった．

Windows での再生成は `libc` と `inBundle` を削り落とす．
先行するノートがこの観察を記録し，1 行の手編集で回避している．
今回は 3 つの依存が動くため，同じやり方では届かない．

---

## ⚖ 判断

- 3 件を 1 本の PR で扱う．いずれも既存の宣言範囲に収まり，切り分ける利点が無いためである．
- `package.json` は `vitest` だけ `^3.0.0` から `^3.2.7` へ上げる．修正版を下限として残す．
- `vite` と `esbuild` はロックファイルだけを動かす．宣言範囲の内側で解決できるためである．

表 1. 解消した 3 件と範囲内である根拠

| 深刻度 | パッケージ | 変更 | 根拠となる宣言 |
|---|---|---|---|
| critical | `vitest` | 3.2.4 → 3.2.7 | `package.json` の `^3.0.0` |
| high | `vite` | 7.3.2 → 7.3.6 | `vite-node` の `^5.0.0 \|\| ^6.0.0 \|\| ^7.0.0-0` |
| low | `esbuild` | 0.27.7 → 0.28.2 | `vite` の `^0.27.0 \|\| ^0.28.0` |

`vite` はトップレベルの 8.2.2 が別に存在する．勧告の対象は入れ子の 7 系だけである．
`vitest` と `vite-node` の 2 か所に入れ子があり，両方を動かす必要があった．

## 🪟 部分適用の手順

再生成の結果をそのまま採らず，変わったエントリだけを本体へ写す．手順は次のとおり．

1. スクラッチパッドへ `package.json` と `package-lock.json` を複製する．
2. 複製の側で `npm install --package-lock-only` と `npm update` を走らせ，目標状態を求める．
3. 版が変わったエントリと，増減したエントリを Node スクリプトで列挙する．
4. 増減の内訳を，重複解消による正当な削除と，再生成による欠落とに仕分ける．
5. 本体へは，差し替えと正当な削除だけを写す．全面置換はしない．

今回の内訳は，差し替えが 37 件，削除が 27 件，保持が 2 件である．
削除は `node_modules/tsx/node_modules/` 配下に限られる．
トップレベルの `esbuild` が 0.28.2 になり，`tsx` の宣言 `~0.28.0` を満たしたためである．
保持したのは `@tailwindcss/oxide-wasm32-wasi` の `@emnapi` 系である．
これは wasm32-wasi 向けの同梱依存であり，Windows では解決できず落ちる．

### 適用の妥当性を機械で確かめる

目視では追えない量になるため，判定を 3 つのスクリプトへ分けた．

- 差し替え前に，旧エントリだけが持つ鍵を検査する．見つかれば適用を中断する．
- 適用後の差分に `libc` と `inBundle` の削除行が無いことを確かめる．
- `integrity` と `resolved` をレジストリの `dist.integrity`・`dist.tarball` へ突き合わせる．

3 つ目は 14 エントリを抽出して実施し，不一致は 0 件だった．
`npm ci` が成功し，かつロックファイルを書き換えないことも確認の一部とした．
ただし `npm ci` の成功は整合の証明ではない．改竄された `integrity` でも，
その値と一致する tarball を取得できれば通るためである．突合はそこを補う．

`JSON.stringify(obj, null, "\t")` に改行を足した結果は，このリポジトリの
ロックファイルとバイト単位で一致する．JSON として読み書きしても書式は崩れない．

## 🔍 外れた前提

### `npm install --package-lock-only` は範囲内で上げない

最初に複製の側で `npm install --package-lock-only` を引数なしで走らせた．
結果は `up to date` であり，`vitest` は 3.2.4 のままだった．
既に宣言範囲を満たすエントリは，このコマンドでは動かない．
対象を `vitest@^3.2.7` のように名指しするか，`npm update <名前>` を使う必要がある．

「再生成すれば最新へ揃う」という理解は成り立たない．
この誤解のままだと，脆弱性が残ったことに気づかないまま作業を終える．

### Dependabot のグループは範囲内の patch を出さない

Issue #169 は「`npm-minor-and-patch` グループが patch 更新を拾う想定」と書いていた．
`vitest` の `dist-tags.latest` は 5.0.0 である．
Dependabot が起票するのは 3 から 5 への major 更新側になる公算が高い．
`^3.0.0` の内側に収まる 3.2.7 への更新は，グループからは出てこない．

宣言範囲がメジャー 1 つぶん遅れている依存では，待っても範囲内の更新は届かない．
手で上げる判断が要る．

ただし脆弱性を伴う更新は，同日に有効化した security updates が拾う見込みである．
実際に範囲内の更新を PR として出すかは未検証である．
経緯は [🛡 脆弱性の勧告が届く経路を用意する](2026-09-04-vulnerability-alert-path.md) を参照．

## 🤖 Bot レビューの読み方

観点を 4 つ添えて Codex へレビューを依頼した．返答は指摘なしの定型文である．
依頼した観点を個別に検証した記述は無かった．

指摘が無いことと，観点が検証されたことは別である．
そこで機械で確かめられる 2 点を手元で追加検証した．

- `integrity` と `resolved` の突合（前掲）．
- `tsx` が実際に解決する `esbuild` の位置．

2 つ目は重要である．`tsx` は `.github/workflows/update-gtfs.yml` の
`npx tsx scripts/convert-gtfs.ts` で使う．重複解消の影響が及ぶ経路にあたる．
確認すると，トップレベルの `node_modules/esbuild` を指し `tsx v4.23.12` が起動した．
削除前の入れ子も 0.28.2 であったため，`tsx` から見える版は変わらない．

## 💡 一般化できる教訓

- パッケージマネージャの「更新」は，宣言範囲の内側にある差を自動では埋めない．
- 増減したエントリは，正当な重複解消と環境由来の欠落とに仕分けてから扱う．
- 目視で追えない量の差分は，判定条件をスクリプトへ書き，違反時に止める．
- Bot の「指摘なし」は，依頼した観点の検証結果とは限らない．確かめた範囲を自分で記す．
