# 🔒 Node の版宣言を 1 か所へ寄せた

`jsdom` 30 が Node の下限を上げ，ローカルの版が要求を満たさなくなった．警告は出ていたが，リポジトリに版の記録が無いため，どこを直せばよいか決められない状態だった．残すのは 3 点である．宣言の寄せ先，`>=` から `^` へ狭めた経緯，そして Windows での再生成を避けた理由である．

## 🚨 発端

`jsdom` 30 は Node の下限を `^22.22.2 || ^24.15.0 || >=26.0.0` へ上げた．ローカルは v22.20.0 であり，`npm ci` が毎回警告を出す．

```text
npm warn EBADENGINE   package: 'jsdom@30.0.1',
npm warn EBADENGINE   required: { node: '^22.22.2 || ^24.15.0 || >=26.0.0' },
npm warn EBADENGINE   current: { node: 'v22.20.0', npm: '11.6.1' }
```

テストは 494 件すべて通る．実害は出ていない．問題は別のところにある．リポジトリには `engines` と `.nvmrc` のどちらも無く，workflow が `node-version: 22` と書いていた．この指定は 22 系の最新へ解決される．つまり CI が実際に何で動いているかは，書いてある値からは分からない．

ローカルと CI がずれていても，ずれ自体を検知できない状態だった．

## 🧭 宣言を 1 か所へ寄せる

版を書く場所は 3 つある．`.nvmrc`，`package.json` の `engines`，workflow の `node-version` である．3 か所に別々の値を書けば，いずれ食い違う．

採った形は次のとおりである．

表 1. 版の宣言と，それぞれが担う役割

| 場所 | 書く内容 | 役割 |
|---|---|---|
| `.nvmrc` | `22` | 使う系を 1 か所で決める．`nvm use` の入力にもなる |
| `engines.node` | `^22.22.2` | 満たさない環境で `npm ci` に警告を出させる |
| workflow | `node-version-file: .nvmrc` | CI がローカルと同じ系を選ぶ |

`.nvmrc` へ正確な版（`22.23.2` など）を書く案は採らなかった．`.nvmrc` を追跡する仕組みが無く，書いた瞬間から陳腐化が始まるためである．Dependabot も対象にしていない．

メジャー版だけを書けば，ローカルの `nvm use` と CI の双方が 22 系の最新を選ぶ．実際の下限は `engines` が担う．マージ後の CI では `node: v22.23.2` が選ばれ，要求を満たしていることを確認した．

## 📐 範囲を系へ閉じる

`engines.node` は当初 `>=22.22.2` と書いた．レビューで指摘を受けて `^22.22.2` へ狭めた．

`>=22.22.2` は Node 23 系・24.15.0 未満・25 系まで含む．いずれも `jsdom` 30.0.1 が拒む版である．宣言と README が，実際には動かない環境へ開発者を誘導していた．

`jsdom` の 3 分岐をそのまま写す案は採らなかった．理由は 2 つある．

1 つは実態との一致である．`.nvmrc` と 3 つの workflow は 22 系だけを使う．宣言もその 1 本へ閉じる方が正確である．

もう 1 つは追随の手間である．依存側の範囲を写すと，依存が動くたびに同期が要る．同期が漏れれば，今回と同じずれが別の形で再発する．

なお `engine-strict` は置いていない．`engines` は警告にとどまり，範囲外でも `npm ci` は成功する．強制するかは別の判断である．

## 🪟 ロックファイルを Windows で再生成しない

`@testing-library/dom` を `devDependencies` へ足す際，`npm install` を Windows で実行した．`package.json` へ 1 行入る一方，`package-lock.json` は 19 行の追加と 78 行の削除になった．

表 2. Windows での再生成で失われた情報

| 失われたもの | 対象の例 |
|---|---|
| `libc` の指定 | linux 向け optional 依存（`glibc` / `musl` の別） |
| `inBundle` のエントリ | `@tailwindcss/oxide-wasm32-wasi` の同梱依存 |

`npm install --package-lock-only` でも同じ結果になった．いずれも実行環境に無いプラットフォーム向けの情報である．Linux で生成された記述を，Windows から実行したことで削り落とした形になる．

採った回避は最小の手編集である．ロックファイルの root にある `devDependencies` へ 1 行だけ足した．該当パッケージ自体は推移的な依存として既にツリーへ載っており，エントリの追加は要らない．

編集の妥当性は `npm ci` で確かめた．成功し，かつロックファイルを書き換えなかった．CI（Linux）でも `npm ci` は成功している．

ここで示したのは 1 行を足す場合の手順である．複数エントリの版を同時に動かす場合は届かない．その手順は [🔐 ロックファイルを Windows で部分適用する](2026-09-04-lockfile-partial-apply.md) へ分けた．

## 🧾 宣言のずれをテストで縛る

宣言を 3 か所へ分けた以上，ずれは必ず起きる．検査を `test/dev-environment.test.ts` へ置いた．

- `.nvmrc` がメジャー版だけを記録する．
- `engines.node` が `^` 形式で，`.nvmrc` と同じメジャー版を指す．
- `setup-node` を使う 3 つの workflow が `node-version` を直書きせず `.nvmrc` を参照する．
- `@testing-library/dom` が `devDependencies` にある．

workflow の一覧はテスト側へ直書きしている．新しい workflow が `setup-node` を使い始めても自動では気づけない．全 workflow を走査する案もあるが，`update-osm.yml` のように node を使わないものと区別できず，かえって縛りが緩む．現状は 3 本の明示を選んだ．

## 💡 一般化できる教訓

- 依存が要求する版と，自分が使う版は別に管理する．前者を写すと同期が終わらない．
- 「どこにも書いていない」状態は，値が間違っている状態より気づきにくい．
- `>=` は範囲を広げすぎる．支えていない環境まで宣言してしまう．
- ロックファイルはプラットフォーム依存の情報を持つ．生成した環境と別の環境で再生成しない．
- 手編集したロックファイルは `npm ci` で検算する．書き換えが起きなければ整合している．
