## 🚨 発端

reviewdog の Lint summary が textlint の指摘を 180 件報告していた．いずれも既存ファイルへ蓄積したものであり，reviewdog は非ブロッキングのため CI は緑のまま増え続けていた．

害は件数そのものではない．ドキュメントへ 1 行触れるだけで，そのファイル全体の指摘が summary へ載る．[PR #141](https://github.com/tomio2480/asahikawa-bus-departure/pull/141) では表の 1 行を足しただけで差分の列に 40 件が並んだ．新規に持ち込んだ指摘が既存分へ埋もれ，毎回 inline の件数を別途数える必要があった．

## 🔍 全件を手元で得る

[Issue #142](https://github.com/tomio2480/asahikawa-bus-departure/issues/142) は「ローカルに textlint は導入しておらず，内訳の全件確認は Actions ログで行う」としていた．この前提は誤りである．個別の指摘は Actions ログに残らず，reviewdog へ流れるだけである．

pin していた中央 action の版（v2.13.8）には，生レポートを artifact へ添付する `upload-reports` が無かった．つまり当時の構成では，全件を得る経路がどこにも無かった．

実際には中央リポジトリの `bin/lint-md.sh` が使えた．呼び出し元リポジトリで CI と同じ設定・同じ lockfile・同じ集計スクリプトを走らせるもので，呼び出し元へは何も置かない．

```bash
bash /path/to/github-workflows/bin/lint-md.sh --all
```

得られた件数は textlint 180 件・markdownlint 0 件であり，CI の報告と一致した．

着手前に pin を v2.16.0 へ更新した（[PR #158](https://github.com/tomio2480/asahikawa-bus-departure/pull/158)）．結果として artifact の経路も開いた．なお lint の規則ファイルと lint 依存の `package-lock.json` は両版で同一であり，更新によって指摘内容は変わらなかった．

## 📊 内訳が示したもの

180 件は 2 ファイルへ集中していた．`docs/REVIEW_LESSONS.md` が 140 件，`docs/ARCHITECTURE.md` が 40 件である．

表 1. ルール別の件数と対処

| ルール | 件数 | 対処 |
|---|---|---|
| `prh`（全角コロンの前後の半角スペース）| 66 | 空白を落とす |
| `sentence-length` | 65 | 文を分ける |
| `ja-no-space-around-parentheses` | 30 | 空白を落とす |
| `no-doubled-joshi` | 7 | 文を分けるか助詞を替える |
| `prh`（全角中黒の前後の半角スペース）| 5 | 空白を落とす |
| `max-kanji-continuous-len` | 4 | 「の」を補う |
| `prh`（表記ゆれ）| 3 | 語を改める |
| `no-mix-dearu-desumasu` | 1 | 誤検出のため設定で外す |

101 件は全角記号に隣接する半角スペースの削除だけで済む．文言を 1 文字も変えない．これを最初の 1 コミットへ分けた．両ファイルから半角スペースとタブを除いた文字列が変更前後で一致することを機械的に確かめてあるため，レビューでは読み飛ばせる．

残る 79 件が文章の書き換えを要する．件数の見た目ほど作業量は均一でない．性質ごとにコミットを分けたのは，この非対称をレビューへ伝えるためである．

## 🧱 出典つき箇条書きと 80 字の衝突

`docs/REVIEW_LESSONS.md` の指摘例は次の形で書かれていた．

```markdown
- **指摘例**（PR #98 CodeRabbit， `src/components/RouteRegistration.tsx` L145）：説明
```

textlint は `：` を文の区切りとみなさない．そのため，この定型先頭と最初の文がひとつの文として数えられる．

表 2. 定型先頭が長い箇条書き

| 定型先頭 | 説明に使える残り |
|---|---|
| 90 字 | -10 字 |
| 89 字 | -9 字 |
| 77 字 | 3 字 |
| 76 字 | 4 字 |

上位 2 件は，説明をどれだけ分けても 80 字へ収まらない．文を分けるという手段が原理的に届かない．

採った解は，括弧に PR / Issue 番号とツール名だけを残し，ファイルパスと行番号を続く文へ移すことである．情報は 1 つも落ちない．

同種の壁がもう 1 つあった．`setSubmitting(true) → try { ... } finally { ... }` は，コードスパン 1 つで 95 字ある．コードスパンの内側は分割できない．順序を 3 つの文へ分け，各段階を個別のコードスパンとして示す形へ改めた．

**1 文の上限は，文の書き方だけでなく文書の記法を縛る．** 出典を括弧で持つ書式や，長い識別子をコードスパンで示す書式は，上限と衝突しうる．衝突したときに動かすのは文ではなく記法である．

## 🚫 誤検出を外す範囲

`no-mix-dearu-desumasu` の 1 件は誤検出であった．「エラーメッセージの句点・文体統一」の節は，句点の揺れの実例として `` `...です。` `` を引用する．地の文はである調で揃っているが，コードスパンの中身まで文体判定の対象に入る．

当初はリスト全体を `disable` と `enable` のコメント対で囲んだ．箇条書きの途中へ `enable` を差し込むとリストが 2 つに分かれるため，それを避けたためである．

これは Codex のレビューで指摘を受けた．誤検出の原因は 1 項だけであり，広く囲うと残り 3 項へ後から文体の混在が入っても検出されない．リストが分かれること自体に実害は無く，検査対象として残る利点のほうが大きい．

範囲を 1 項へ絞った状態でも指摘は 0 件のままであった．**この結果は，原因が本当にその 1 項だけであることの裏づけにもなる．** 除外の範囲を狭めることは，安全側へ寄せる操作であると同時に，原因の切り分けでもある．

なお行単位の `textlint-disable-next-line` は，この action の filter 構成では効かない．`disable` と `enable` の対で挟む必要がある．

## 🤖 機械検査の後に残るもの

textlint が 0 件になった時点で Codex のレビューを依頼した．機械で測れる部分は通り切っているため，観点を人の判断が要る部分へ絞って添えた．

返ってきた 5 件は，すべて文を分ける過程で混入した意味のずれであった．

表 3. Codex の指摘と性質

| 指摘 | 性質 |
|---|---|
| 同期の依存方向が逆に読める | 派生値と依存元を取り違えた |
| 空白期間の発生主体が変わった | 能動形へ変えて主体が暗黙の作業者へ移った |
| 除外範囲が広すぎる | コメントの説明と実際の範囲が食い違う |
| 「別々に」の掛かり先が片方だけ | 分割で修飾関係が切れた |
| 「1 つ」が数量に読める | 対応づけの語を失った |

**いずれも textlint では検出できない．** 文長・助詞・表記は機械が見るが，文を分けたときに因果・修飾・主体がどう動くかは見ない．機械検査を 0 件にする作業は，それ自体が別種の欠陥を作り込む工程である．

指摘のうち 2 件は，提案どおりの文にすると `no-doubled-joshi` が再発する．文意を戻すことと機械検査を通すことは同時に満たす必要があり，どちらか一方を優先すると往復する．文を分けて各文の助詞を 1 回に抑えることで，両方を満たした．

## 💡 一般化できる教訓

- **既存指摘の棚卸しでは，まず全件を得る経路を確かめる．** 経路が無いまま件数だけを見ても，作業量も難所も見積もれない．今回は Issue に書かれた前提自体が誤っていた．
- **機械的に片づく分を最初の 1 コミットへ分ける．** 差分が空白の削除だけであることを機械で確かめておけば，レビューはそこを読み飛ばせる．今回は 180 件のうち 101 件がこれに当たる．
- **1 文の上限は文書の記法を縛る．** 分割で届かない衝突に当たったら，文ではなく記法を動かす．
- **除外の範囲は原因の最小単位まで絞る．** 絞った状態で指摘が出ないことは，原因の切り分けを兼ねる．
- **機械検査を 0 件にした後こそレビューを受ける．** 通ったことは正しさの証拠にならない．文を分けた箇所は，因果・修飾・主体が動いていないかを人が見る必要がある．
