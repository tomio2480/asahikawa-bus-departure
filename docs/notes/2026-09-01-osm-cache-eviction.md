# 🗺 OSM キャッシュの退避と pfaedle の無言スキップ

2026-09-01 に `Update OSM Data` が Geofabrik の HTTP 502 で失敗した．その調査で，Actions のキャッシュが 7 日で退避される性質とワークフローの条件分岐が噛み合っていた事実を掴んだ．経路形状の生成は長期にわたりスキップされていた．本書は経緯と対処，一般化できる教訓を残す．

## 🔎 発端

月次の `update-osm.yml` が失敗した（[run 33479590413][run]）．Geofabrik が HTTP 502 を返し，`curl -f` が終了コード 22 で落ちた．

再試行の設定は `--retry 3 --retry-delay 5` であり，約 20 秒しか粘れていない．上流の一時障害であってリポジトリ側の欠陥ではない．調査時点で Geofabrik は復旧しており，同じ URL から 188 MB の取得に成功した．

ここで止めれば「再実行して終わり」だった．ただし失敗したワークフローが何のために存在するかを追ったところ，別の問題へ行き着いた．

---

## 🕳 二段目の問題

`update-osm.yml` の役目は OSM データを Actions のキャッシュへ置くことだけである．実際に使うのは週次の `update-gtfs.yml` であり，キャッシュを復元して pfaedle へ渡す．

しかし `gh cache list` に `osm-hokkaido-` で始まる項目が存在しなかった．Actions のキャッシュは 7 日間アクセスがないと退避される．月次で保存しても，週次のワークフローが必要とする時点では失われている．

さらに pfaedle のステップが次の条件を持っていた．

```yaml
if: steps.calendar.outputs.changed == 'true' && hashFiles('data/osm/hokkaido-latest.osm.pbf') != ''
```

キャッシュが無ければ条件が偽となり，ステップごとスキップされる．ジョブは緑のまま完了する．2026-08-24 の実行ログでも `Cache not found for input keys: osm-hokkaido-` を確認した．カレンダー変更を検知して変換まで走った回でも，経路形状は生成されていなかった．

## 🧩 原因の構造

<!-- 図表キャプションは体言止めとし句点を付けない．該当行のみ規則を外す． -->
<!-- textlint-disable-next-line ja-technical-writing/ja-no-mixed-period -->
表 1. 2 つの前提と，それらが噛み合って生んだ結果

| 前提 | 単体では妥当 | 組み合わせた結果 |
|---|---|---|
| キャッシュは 7 日でアクセスがなければ退避される | GitHub 側の仕様 | 月次保存では週次利用に間に合わない |
| ステップの条件に `hashFiles` を置く | 入力が無ければ動かさない自然な発想 | 失敗が緑のジョブとして埋もれる |

`scripts/run-pfaedle.sh` には，OSM ファイルが無ければ Geofabrik から取得するフォールバックが元から実装されていた．皮肉なことに，そこへ到達する前にワークフローの条件がステップごと消していた．防御を二重に用意し，外側が内側を無効化していた形である．

---

## 🛠 対処

対処は [PR #119][pr119] で行った．

<!-- textlint-disable-next-line ja-technical-writing/ja-no-mixed-period -->
表 2. 変更の内容と意図

| 変更 | 意図 |
|---|---|
| curl の再試行を `--retry 5 --retry-delay 20 --retry-all-errors --retry-max-time 600` へ拡張 | 数分規模の一時障害を吸収する |
| pfaedle ステップの `hashFiles` ガードを撤去 | フォールバックへ到達させ，失敗を赤いジョブとして表面化させる |
| キャッシュミス時に取得した pbf を保存し直すステップを追加 | 次回実行へつなぎ，取得の重複を避ける |
| フォールバック取得へ md5 検証を追加 | 破損した pbf で劣化した経路形状を作らない |
| 作業用の `/data/` を `.gitignore` へ追加 | 190 MB の pbf を誤って追跡しない |

`.gitignore` は `/data/` と先頭スラッシュ付きで書く．`data/` と書いた場合，追跡下の `public/data/` まで巻き込む．結果としてワークフローの `git add public/data/` が新規ファイルを拾えなくなる．

## 💡 一般化できる教訓

- **キャッシュの保存周期は，利用側の周期より短く保つ．** 保存側だけを見ると月次で足りるように見える．退避の期限を挟むと成立しない．
- **入力の有無でステップを分岐させない．** 分岐は失敗を成功に見せる．入力を用意する責任はステップの内側へ寄せ，足りなければ落とす．
- **緑のジョブは正常の証拠にならない．** 条件付きステップを持つワークフローでは，何が実行されたかまで見ないと劣化を検知できない．
- **失敗したジョブは，何のために存在するかまで遡る．** 今回は一過性の 502 が入口となり，半年近く気づかれなかった欠落へ届いた．

## 🚧 残る課題

キャッシュの退避そのものは避けられない．週次のワークフローがカレンダー変更を検知した週は，190 MB の取得が発生する．ランナー上では 1 分程度の追加と見込むが，実測は次の該当週まで得られない．

また，経路形状が実際に生成されたかを継続的に監視する仕組みは無い．現状は失敗すればジョブが落ちる状態までを担保している．
